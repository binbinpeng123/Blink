# 本地存储引擎设计

评审状态：已允许开发
评审人：binbinpeng123
评审日期：2026-10-23
适用版本：v0.1.0（首个可用版本）

## 目标

为单节点边缘部署设计可恢复、可校验、适合大对象顺序读写的本地数据布局和访问路径，同时保留未来分布式扩展的接缝。

## 与主流方案的对比

| 方案 | 元数据组织 | 数据布局 | 校验 | 面向场景 | Blink 的取舍 |
| --- | --- | --- | --- | --- | --- |
| **MinIO** | 每对象元数据文件 | 纠删码分片 | 每对象 | 单二进制与分布式 | **借鉴**：单二进制、每对象元数据、Go 生态；**放弃**：纠删码（单节点收益小、复杂度高） |
| **SeaweedFS** | 中心 filer + volume 索引 | needle 追加打包 | volume 级 | 海量小文件 | **借鉴**：小对象打包思路（创新 D，仍未实施）；**放弃**：master/volume/filer 三层架构，对单节点过重 |
| **Garage** | 独立键值存储 | 固定大小块 | 块级 | 地理分布的小集群 | **借鉴**：块管理模型；**放弃**：为多节点复制设计，依赖外部存储引擎 |
| **Ceph RGW** | RADOS 对象 | 完整集群 | 多级 | 大规模统一存储 | **整体排除**：边端无法承载 |
| **versitygw / s3proxy** | 直接 POSIX 映射 | 原样文件 | 无 | 简单网关 | **借鉴**：协议层可直接映射；**放弃**其做法（无校验、无恢复、无 AI 场景优化）—— 这正是 Blink 要填补的空白 |

**结论**：Blink 采用"单二进制（MinIO 式）+ 块管理（Garage 式）+ 自研校验与恢复"，不引入外部键值引擎。**v0.2.0 起在同一二进制中加入多副本与可选纠删码**（见 08 文档）；单机模式仍是默认路径，存储格式与写读路径不变，EC 只作为大对象的一种额外布局。

## 数据布局

```text
<data-dir>/
  blink-meta.json                # 格式版本、node_id、创建时间
  buckets/
    <bucket>/
      bucket.json                # 创建时间
      cors.json                  # 桶级 CORS 配置（可选；与 bucket.json 分离）
      objects/
        <sha256(key) 前 2 位>/
          <sha256(key)>/
            meta.json            # 对象元数据（见下）
  cas/                           # 内容寻址块存储
    <sha256 前 2 位>/
      <sha256>                   # 只读、只增、不可变
  tmp/                           # 写入暂存，启动时清扫
  multipart/<uploadId>/          # 分片上传状态
```

### 设计取舍

**元数据使用 JSON，而非 WAL 或自定义二进制。** 理由：单节点规模下 JSON 完全够用；可读、可调试、易迁移（边界情况可直接 `cat` 排查）。**明确放弃 WAL + 快照**是为了避免追加结构的崩溃恢复复杂度。

**代价与风险（必须显式记录）**：对象目录名是 key 的 SHA256，因此 LIST 操作必须读取全部 `meta.json` 才能取得原始 key 并排序。**这是本设计最主要的性能风险**，100 万对象规模下 LIST 延迟需要实测。应对措施：切片 9 的分片并行扫描与 LIST 部分字段解码已使本机 10 万对象 LIST 从 17.8 s 降到 4.1 s（Apple M4/APFS，回归基线，非承诺）；小对象打包仍未实施，`BenchmarkList100kObjects` 继续作为回归对照。

**为什么目录名用 `sha256(key)` 而非原始 key**：避免非法字符、超长路径与路径遍历问题。代价是上述 LIST 开销 —— 这是刻意的取舍，不是疏忽。

**块采用内容寻址**：块文件名即其内容的 SHA256。这带来两个天然收益：

1. **完整性自校验**：读取时可验证块内容与文件名一致。
2. **跨桶、跨 key 天然去重**：同一模型分片被多次写入（不同 bucket、不同 key、或分片上传后重传）时，重复块不会被重复存储。

### meta.json 字段

| 字段 | 说明 |
| --- | --- |
| `version` | 元数据格式版本 |
| `key` | 原始对象 key |
| `size` | 对象字节数 |
| `etag` | 见 02 文档的 ETag 规则 |
| `content_type` | MIME 类型 |

| `checksum` | 对象级校验和（算法按客户端声明） |

## 块策略

| 参数 | 取值 |
| --- | --- |
| 块大小 | 4 MiB |
| 小对象内联阈值 | 64 KiB |
| 校验算法 | 每块 CRC32C（硬件加速） |
| 块命名 | 内容 SHA256 |

- 小对象（≤ 64 KiB）仍按内容寻址存储，但不做额外分片。
- 大对象顺序切分为 4 MiB 块，逐块计算 CRC32C 并写入 CAS。
- 流式切块的临时缓冲按 `min(Content-Length, 块大小)` 分配，且小对象先按内联阈值分配、确认超阈值后才增长：1 KiB PUT 的内存分配从 4.2 MB 降到约 11 KB，1 MiB 从 4.2 MB 降到 1.13 MB，块边界不变（`StreamBlocksSized`，见 [09 文档](./09-edge-io-performance.md)）。
- 块级 SHA-256 与 CRC32C 在独立 goroutine 中计算，与整对象 MD5（ETag）重叠：MD5 是链式的、标准库又是纯 Go 实现，无法并行；把有硬件加速的 SHA-256/CRC32C 从 MD5 的关键路径上移走。仅当 `GOMAXPROCS > 1` 且块长 ≥256 KiB 时启用，小对象仍走原来的串行路径；回调返回前等待块级哈希完成，块缓冲的复用语义不变（见 [09 文档](./09-edge-io-performance.md)）。
- 客户端声明的对象级校验和（如 CRC64NVME、SHA256）独立于块级 CRC32C，两者同时记录。
- CRC64NVME 标准库只有 ISO/ECMA 两个预设，没有 NVME 多项式，需自备多项式常数。**注意**：标准库的 `hash/crc64` 并非只有逐字节实现，它本身就有 slicing-by-8；差别在于非内置多项式**每次调用都现建一张 16 KiB 表**，而对象级校验和是分块流式喂入的，这笔开销正好落在热路径。实测差别随分块大小变化：8 KiB 分块 +24%、32 KiB +6%、4 MiB 持平（Apple M4，仅作回归基线）。因此自维护表是"消除对喂入粒度的依赖"，不是"算法更快"——后者是常见误传，已在 `internal/checksum/` 中留下实测数据与更正记录。

## 写路径

原子写入序列，每一步都可被故障注测试覆盖：

```text
1. 写入 tmp/<随机名>            （边写边计算块 CRC 与客户端声明的校验和）
2. fsync 数据文件
3. 将块提交到 cas/<xx>/<sha256>  （内容寻址；若已存在则跳过，即去重）
4. 写 tmp/<随机名>.meta         （新元数据）
5. fsync 元数据文件
6. rename 到 objects/<xx>/<sha256>/meta.json   （原子替换）
7. fsync 父目录
```

**关键保证**：第 6 步的 `rename` 是原子的。崩溃发生在第 6 步之前 → 对象不存在（旧版本仍在）；发生在第 6 步之后 → 对象为完整新版本。**任何时刻都不会出现"对象存在但内容残缺"的状态。**

`--fsync-policy` 可配置为 `always`（默认，每步 fsync）或 `meta`（仅元数据 fsync，吞吐更高、掉电窗口更大）。这是可靠性与吞吐的显式权衡，默认取可靠性。

## 读路径

- 大对象 GET 使用 `sendfile` 零拷贝：定位偏移、声明 `Content-Length`、直接搬运数据，避免用户态缓冲区拷贝。
- Range 请求在块边界内直接定位，不读取无关块。
- 对象元数据带**有界 LRU 缓存**（默认 4 MiB / 1024 条，单条 ≤128 KiB）；写、覆盖写、删除与副本元数据变更时同步更新或失效。缓存只服务 `OpenObject` 等点查路径，LIST 仍直接扫盘，不着色结果。命中后 1 KiB GET 从 113–159 µs 降到 55–58 µs（详见 [09 文档](./09-edge-io-performance.md)）。

### 真实张力：校验读 vs 零拷贝读

**验证读（逐块校验和）与零拷贝读（sendfile）在原理上互相冲突**：校验必须将数据读入用户态，零拷贝则刻意避开用户态。

面向边端真实负载取舍：

- **写入时**：全量校验（CRC32C + 客户端声明的校验和），确保落盘数据正确。
- **读取时**：默认**不**逐块校验，走零拷贝路径，保障模型加载吞吐。
- **后台**：独立的后台 goroutine 按周期（默认 24h，`--integrity-interval` / `BLINK_INTEGRITY_INTERVAL`）顺序巡检全部对象，以单流低优先级读盘重算 CRC32C，检出静默损坏并记录指标与日志。详见下文"后台完整性巡检"。
- **可选**：按 bucket 或全局配置启用"读取时校验"，用于对可靠性要求高于吞吐的场景。

两模式的性能差距必须由 `BenchmarkGetRangeSequential`（零拷贝）与开启校验后的对照数据量化，**不得只凭推断**。

## 崩溃恢复

启动流程设计目标是**与已存对象数量弱相关**，不做全量数据扫描：

1. 读取并校验 `blink-meta.json`；若格式版本高于本二进制支持的版本，**拒绝启动**并给出明确错误（防止旧版本损坏新数据）。
2. 清扫 `tmp/` 中的残留文件 —— 这些必然是未提交的写入。
3. 清扫未完成的分片上传（超过保留期的 `multipart/` 状态）。
4. 桶目录自愈：`bucket.json` 缺失或损坏时按最小元数据重建，而非让整个桶不可用。
5. 启动后台 GC 与完整性巡检（scrub）。**巡检首轮不在启动时触发**，而是在第一个周期之后开始：边端 Pod 滚动重启频繁，启动即全盘扫描会把每次重启后的前台读延迟打满。

**明确不做**：启动时不遍历 `cas/` 做完整性全盘校验（代价与对象数量成正比，违背"与规模弱相关"目标）。损坏在读取或 scrub 时才发现并上报。

**限制**：macOS 上无法可靠模拟掉电，因此"fsync 后 rename 前"这一关键窗口由故障注入测试覆盖；真实掉电场景**未测试**，记录在 `docs/design/known-limitations.md`。

## 并发与锁

| 场景 | 策略 |
| --- | --- |
| 同一 key 的并发写 | 对象级锁，最终以最后一次原子 `rename` 为准，读者不撕裂 |
| 不同 key 的并发写 | 完全并行，互不阻塞 |
| 读与写并发 | 无锁；依赖 `rename` 原子性与 CAS 不可变性 |
| 分片上传 | 各分片独立写入，`CompleteMultipartUpload` 时统一提交 |

## 垃圾回收

- **孤儿块**：CAS 中未被任何 `meta.json` 引用的块。带**宽限期**（默认 1 小时）后回收，避免误删在途写入的块。
- **临时文件**：启动时清扫 + 定期清扫超过保留期的残留。
- **分片上传残留**：超过保留期的未完成上传自动中止并清理。
- **可回收空间**：通过 `blink_disk_reclaimable_bytes` 指标暴露，让运维理解"删除对象后空间未立即释放"是由于去重共享或宽限期。

**去重的语义边界**：同一内容被多个对象引用时，删除其中一个对象不会释放空间（其它对象仍引用该块）。这一点必须在文档中明确，避免用户误认为删除立即释放磁盘。

## 后台完整性巡检（scrub）

读取时校验只在对象被访问时发现损坏，长期不被读取的冷数据可能坏了很久都无人知晓。后台巡检主动把本节点上的对象逐个读一遍，把"静默损坏"转成可告警的指标与日志。

| 项 | 行为 |
| --- | --- |
| 触发 | 独立 goroutine，按 `--integrity-interval` / `BLINK_INTEGRITY_INTERVAL` 周期执行；默认 24h，`<=0` 禁用 |
| 首轮 | **延迟一个周期**，不在启动时立即执行（避免 Pod 滚动重启反复触发全盘扫描） |
| 顺序 | 逐对象、逐块顺序读取，天然把磁盘读带宽限制在单流水平，避免与前台读竞争 |
| 校验 | 只重算块级 CRC32C，不重算 SHA256；与读取时校验复用同一实现 |
| 缓存 | **绕过** `metaCache` 直接读盘，否则缓存会掩盖 `meta.json` 损坏与陈旧块表 |
| 列举 | 单次 `ListObjects` 取全桶（`ListObjects` 每页都会重扫整个桶，翻页会退化为 O(n²)） |
| 损坏 | 只计数并记录明细（最多 100 条），**不中断**整轮；其余对象继续检查 |
| 并发删除 | 巡检期间消失的对象/桶计入 `skipped`，不报警 |
| 错误 | 仅列举或读取元数据等系统错误让整轮失败；ctx 取消返回部分统计且**不发布**结果 |

**EC 边界**：EC 对象的 `Blocks[].Hash` 是逻辑整块哈希，本地 CAS 通常不存在；真实数据是分散在环上的分片。巡检只校验**本地存在**的分片，缺失分片交给集群反熵修复。否则每个非组员节点都会把同一批健康对象误报为损坏，告警立即失去意义。非 EC 的集群路径中，meta 只提交给拿到全部块的节点，因此本地应能整块校验。

**指标**（描述最近一轮，不是累计值）：

| 指标 | 含义 |
| --- | --- |
| `blink_scrub_last_scanned_objects` | 本轮完成校验的对象数（含损坏对象） |
| `blink_scrub_last_corrupt_objects` | 本轮检出损坏的对象数 |
| `blink_scrub_last_duration_seconds` | 本轮耗时 |
| `blink_scrub_last_completed_timestamp_seconds` | 本轮完成时刻；0 表示尚未完成过巡检 |

**日志**：`scrub_scheduled`（含首轮延迟）、`scrub_completed`（含耗时与计数）、`scrub_corrupt`（逐条损坏明细）、`scrub_failed`、`scrub_disabled`。

## 磁盘容量管理

| 参数 | 默认值 |
| --- | --- |
| 高水位 | 0.90 |
| 低水位 | 0.85 |

- 超过高水位：拒绝新的写入（PUT / 分片上传），返回 `507 InsufficientStorage`。
- **降至低水位以下才恢复接受写入**（滞回区间，避免在阈值附近抖动）。
- **满盘时读与删除必须仍然可用** —— 否则用户无法通过删除释放空间自救。
- 水位与可回收空间通过 `/readyz` 字段与 Prometheus 指标暴露。

**已确认（2026-10-26）**：满盘返回 `507 InsufficientStorage`，`/readyz` 保持 `200` 并暴露水位字段。依据是主流实现的行为：MinIO 与 Dell ECS/ObjectScale 均以 507 表示容量耗尽，AWS 的 `503 SlowDown` 仅表示请求限流；健康检查不把容量耗尽等同于进程未就绪。详见 `docs/design/known-limitations.md`。

## 创新点

以下创新项面向边端 AI 推理的真实负载。**所有未由基准数据支撑的收益均标注为待验证假设，不得作为性能承诺。**

| 创新 | 本版本 | 实现成本 | 验证方式 |
| --- | --- | --- | --- |
| **A. 内容寻址块 + 每块 CRC32C，跨桶/跨 key 天然去重** | ✅ 纳入 | 低（布局自带） | `BenchmarkDedupSecondCopy/1GiB` 断言写入字节数不增长 |
| **B. 分片上传完成时仅串接块表，不重写数据** | ✅ 纳入 | 中 | `BenchmarkCompleteMultipart20GB` 断言耗时与写入量不随对象增长 |
| **C. `sendfile` 零拷贝读路径 + 顺序预读** | ✅ 纳入 | 低 | `BenchmarkGetRangeSequential` 前后对照 |
| **D0. 小对象内容内联进 `meta.json`** | ✅ 纳入（默认 ≤4 KiB，`0` 关闭） | 中 | `BenchmarkGetSmallInline`、`BenchmarkListSmallInline`、`BenchmarkPutSmallInline` 前后对照 |
| **D. 小对象打包为只读 segment（needle 思路）** | ⏸ 未实施（D0 先落地的过渡方案） | 高 | `BenchmarkPutSmallObject10k`、`BenchmarkList100kObjects` 前后对照 |
| **E. 批量写与非标准 API** | ❌ 不做 | — | 保持"任意 S3 客户端可用"，不引入非标准接口 |
| **F. 预热 / pin 接口** | ❌ 不做 | — | 零拷贝与内核页缓存已使热点模型自然驻留 |
| **F'. TTL bucket（中间结果自动过期）** | ⏸ 配置驱动的后台任务，切片 9 之后 | 低 | 属策略而非机制，不占用首个切片注意力 |

**为什么创新 B 对边缘场景重要**：20 GiB 模型的分片上传若在完成时重写全部数据，在 eMMC/SD 卡上会产生数十 GiB 的额外写入（写放大），显著缩短介质寿命。仅串接块表可将完成操作的开销与对象大小解耦。

**开发纪律**：创新 D 是唯一"必须先有基线基准数据、再决定是否合入"的项。任何没有前后 benchmark 对照的优化一律回滚。

### 创新 D0：小对象内容内联（2026-11-10 落地）

**动机**：边端 AI 负载里大量对象是 4 KiB 以下的配置、prompt 片段、推理结果与
清单。它们走 CAS 时，一次 GET 仍要打开/`Stat` 一个块文件，一次 PUT 要写块文件
再做一次持久化屏障；数据本身只有几 KiB，元数据与文件系统开销占了大头。

**做法**：

- `PutObject` 在 `0 < ExpectedSize <= InlineObjectMaxSize` 时先预读
  `ExpectedSize+1` 字节。长度恰好匹配 → 内容只做 MD5/对象校验和/块哈希计算，
  不写 CAS；长度不符 → `io.MultiReader(prefix, body)` 回退普通流式路径，保持
  原有 `ErrIncompleteBody` 语义。
- 内联对象在 `meta.json` 里新增 `inline_data` 字段（JSON 自动 base64），并保留
  **恰好一个** `BlockDesc`：`Offset=0`、`Length=Size`、`Hash` 为内容的 SHA-256、
  `CRC32C` 为内容的 Castagnoli 校验和。块表因此仍是"内容完整性凭据"的唯一来源，
  读取、巡检、副本校验共用同一套判断。
- 单次原子提交：内联对象只需 `writeFileAtomic(meta.json)` 一次；删除对象即随
  目录释放内容，不产生需要 GC 的 CAS 块。
- ETag 与对象级校验和复用 `StreamBlocksSized` 计算，保证同一份内容无论内联与否
  都得到完全相同的 ETag。
- 作用域仅限单机 `Store.PutObject`。集群写路径由 `cluster/write.go` 自行调用
  `StreamBlocksSized`，不经过该分支；EC 与分片上传也不产生内联对象。
  `clusterReader` 仍按块哈希向副本拉取，遇到内联 meta 会因 CAS 中不存在该块而
  返回 `ErrCorrupt`（响亮失败，不会静默返回空对象）——这是把单机数据目录直接
  接入集群的既有限制，不是本切片的支持范围。

**旧版本兼容**：旧二进制忽略 `layout` 字段，按块表去 CAS 找那个 SHA-256。

- 若同等内容曾以普通块写入并被去重命中，读到完全相同且正确的字节；
- 否则 `copyBlockSegment` 返回 `ErrCorrupt`，不会静默返回空对象。

因此不提升 `FormatVersion`（仍为 1）。这一行为由
`TestInlineOldVersionCompatibility` 覆盖。

**默认值与开关**：服务端默认 `4 KiB`（`--inline-object-max-size` /
`BLINK_INLINE_OBJECT_MAX_SIZE`，`0` 关闭），且不得超过 `inline-threshold`。
store 的 `Options` 零值关闭，避免影响直接调用方与既有测试。

**代价（如实记录）**：内联内容以 base64 存入 `meta.json`，文件按 4/3 膨胀；
LIST 必须读取每个对象的全部元数据，因此内联对象越多、内容越大，LIST 的单次
耗时越高。本机 1000 个 1 KiB 对象 LIST 从 16.1–16.3 ms 升至 18.2–19.1 ms
（+14%～17%），4 KiB 对象为 16.3–16.8 ms → 18.7–19.7 ms（+15%～18%）。收益
与代价的取舍、以及为什么仍默认开启，见 09 文档。

**回滚条件**：内联读写/复制/巡检/副本元数据任一致性测试失败，或内联对象的
ETag 与同一内容的普通对象不一致，或 LIST 回退超过 25%（以
`BenchmarkListSmallCAS` 与 `BenchmarkListSmallInline` 同机对照为准）。

## 分布式扩展点（v0.2.0 已落地）

**v0.1.0 的"预留接缝"大部分只停留在文档，代码中并不存在** —— v0.2.0 从零补齐了这一层，并把预留清单改写为已落地清单。完整设计见 [08 分布式存储设计](./08-distributed-storage.md)。

| 扩展点 | 位置 | 单机行为 | 集群行为 |
| --- | --- | --- | --- |
| `store.Backend` 接口 | `internal/store/backend.go` | `*store.Store` 直接实现，**零额外调用跳转** | `*cluster.Cluster` 实现，内部持有本地 `*store.Store` 作为"副本引擎" |
| `node_id` | `blink-meta.json` | 首次启动生成并持久化 | 由 `BLINK_NODE_ID` 提供，参与 LWW 决胜 |
| 放置 | `internal/cluster/ring.go` | 不参与 | 128 vnode 一致性哈希，`Replicas(key, N)` |
| 块读取 | 块读取路径 | 只读本地 CAS | 本地命中走 `sendfile`，未命中经内部接口流式拉取 |
| 元数据版本 | `meta.json` | `obj_version` 单调递增 | HLC `(physical_ms, counter)` + `node_id` 决胜 |
| 配置段 | `internal/config` | `BLINK_CLUSTER_MODE=single`（默认） | `cluster`，启动时强校验 peers/secret/quorum |

**单机模式的零开销要求**：不启动内部端口、不启动修复/反熵 goroutine、不建立任何 Peer 客户端、不改变存储格式与写读路径。接口抽取的性能回退必须 <3%（以 `BenchmarkGetRangeSequential`、`BenchmarkList100kObjects` 前后对照为准）。

**集群模式下的既有局限（沿用，不假装解决）**：

- **CAS 去重是每节点内的**：同一内容落到不同节点仍各存一份。副本数 N 本身已把空间放大 N 倍，这是 S3 级别的冗余代价，不是缺陷。
- **LIST 成本 ×N**：每节点都要扫本机 `meta.json`，集群 LIST 慢于单机（见 05 文档，不承诺 500ms）。
- **块 GC 仍未实现**：删除对象只删 meta（集群模式写 tombstone），CAS 块不回收；多副本让空间占用更高。

**明确不做**：节点发现、在线成员变更、共识协议（Raft）、跨区域复制、EC 自动换组重编码。

## 验收要求

设计必须给出数据损坏、进程中断、磁盘满和重复写入时的行为；实现必须有恢复测试、并发读写测试和可观测的失败原因。

| 场景 | 要求行为 |
| --- | --- |
| 数据块损坏 | 读取或 scrub 时检出，返回明确错误并记录块哈希，不静默返回错误数据 |
| 进程中断 | 恢复后对象只可能"不存在"或"内容完整"，绝不残缺 |
| 磁盘满 | 写入返回 `507 InsufficientStorage`，临时文件被清理，读与删除仍可用 |
| 重复写入 | 相同内容不重复占用磁盘（去重），且元数据正确指向已存块 |
