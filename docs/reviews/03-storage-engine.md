# 本地存储引擎设计

评审状态：已允许开发
评审人：binbinpeng123
评审日期：2026-10-23
适用版本：v0.1.0（首个可用版本）

## 目标

为单节点边缘部署设计可恢复、可校验、适合大对象顺序读写的本地数据布局和访问路径，同时保留未来分布式扩展的接缝。

## 与主流方案的对比

| 方案 | 元数据组织 | 数据布局 | 校验 | 面向场景 | Blink 的取舍 |
| --- | --- | --- | --- | --- | --- |
| **MinIO** | 每对象元数据文件 | 纠删码分片 | 每对象 | 单二进制与分布式 | **借鉴**：单二进制、每对象元数据、Go 生态；**放弃**：纠删码（单节点收益小、复杂度高） |
| **SeaweedFS** | 中心 filer + volume 索引 | needle 追加打包 | volume 级 | 海量小文件 | **借鉴**：小对象打包思路（延后至切片 9）；**放弃**：master/volume/filer 三层架构，对单节点过重 |
| **Garage** | 独立键值存储 | 固定大小块 | 块级 | 地理分布的小集群 | **借鉴**：块管理模型；**放弃**：为多节点复制设计，依赖外部存储引擎 |
| **Ceph RGW** | RADOS 对象 | 完整集群 | 多级 | 大规模统一存储 | **整体排除**：边端无法承载 |
| **versitygw / s3proxy** | 直接 POSIX 映射 | 原样文件 | 无 | 简单网关 | **借鉴**：协议层可直接映射；**放弃**其做法（无校验、无恢复、无 AI 场景优化）—— 这正是 Blink 要填补的空白 |

**结论**：Blink 采用"单二进制（MinIO 式）+ 块管理（Garage 式）+ 自研校验与恢复"，刻意**不做**纠删码、不引入外部键值引擎、不做多节点复制。

## 数据布局

```text
<data-dir>/
  blink-meta.json                # 格式版本、node_id、创建时间
  buckets/
    <bucket>/
      bucket.json                # 创建时间
      cors.json                  # 桶级 CORS 配置（可选；与 bucket.json 分离）
      objects/
        <sha256(key) 前 2 位>/
          <sha256(key)>/
            meta.json            # 对象元数据（见下）
  cas/                           # 内容寻址块存储
    <sha256 前 2 位>/
      <sha256>                   # 只读、只增、不可变
  tmp/                           # 写入暂存，启动时清扫
  multipart/<uploadId>/          # 分片上传状态
```

### 设计取舍

**元数据使用 JSON，而非 WAL 或自定义二进制。** 理由：单节点规模下 JSON 完全够用；可读、可调试、易迁移（边界情况可直接 `cat` 排查）。**明确放弃 WAL + 快照**是为了避免追加结构的崩溃恢复复杂度。

**代价与风险（必须显式记录）**：对象目录名是 key 的 SHA256，因此 LIST 操作必须读取全部 `meta.json` 才能取得原始 key 并排序。**这是本设计最主要的性能风险**，100 万对象规模下 LIST 延迟需要实测。应对措施：切片 9 的分片并行扫描与 LIST 部分字段解码已使本机 10 万对象 LIST 从 17.8 s 降到 4.1 s（Apple M4/APFS，回归基线，非承诺）；小对象打包仍未实施，`BenchmarkList100kObjects` 继续作为回归对照。

**为什么目录名用 `sha256(key)` 而非原始 key**：避免非法字符、超长路径与路径遍历问题。代价是上述 LIST 开销 —— 这是刻意的取舍，不是疏忽。

**块采用内容寻址**：块文件名即其内容的 SHA256。这带来两个天然收益：

1. **完整性自校验**：读取时可验证块内容与文件名一致。
2. **跨桶、跨 key 天然去重**：同一模型分片被多次写入（不同 bucket、不同 key、或分片上传后重传）时，重复块不会被重复存储。

### meta.json 字段

| 字段 | 说明 |
| --- | --- |
| `version` | 元数据格式版本 |
| `key` | 原始对象 key |
| `size` | 对象字节数 |
| `etag` | 见 02 文档的 ETag 规则 |
| `content_type` | MIME 类型 |
| `modified` | 最后修改时间（UTC） |
| `user_meta` | `x-amz-meta-*` 键值对 |
| `blocks` | 有序块描述列表（每条含块哈希、偏移、长度） |
| `checksum` | 对象级校验和（算法按客户端声明） |
| `node_id` | 写入节点（分布式预留） |
| `obj_version` | 单调递增版本号（分布式预留） |

`checksum` 与 `checksum_algorithm` 需同时记录，以便 `ChecksumMode: ENABLED` 时正确回传。

## 块策略

| 参数 | 取值 |
| --- | --- |
| 块大小 | 4 MiB |
| 小对象内联阈值 | 64 KiB |
| 校验算法 | 每块 CRC32C（硬件加速） |
| 块命名 | 内容 SHA256 |

- 小对象（≤ 64 KiB）仍按内容寻址存储，但不做额外分片。
- 大对象顺序切分为 4 MiB 块，逐块计算 CRC32C 并写入 CAS。
- 客户端声明的对象级校验和（如 CRC64NVME、SHA256）独立于块级 CRC32C，两者同时记录。
- CRC64NVME 标准库只有 ISO/ECMA 两个预设，没有 NVME 多项式，需自备多项式常数。**注意**：标准库的 `hash/crc64` 并非只有逐字节实现，它本身就有 slicing-by-8；差别在于非内置多项式**每次调用都现建一张 16 KiB 表**，而对象级校验和是分块流式喂入的，这笔开销正好落在热路径。实测差别随分块大小变化：8 KiB 分块 +24%、32 KiB +6%、4 MiB 持平（Apple M4，仅作回归基线）。因此自维护表是"消除对喂入粒度的依赖"，不是"算法更快"——后者是常见误传，已在 `internal/checksum/` 中留下实测数据与更正记录。

## 写路径

原子写入序列，每一步都可被故障注测试覆盖：

```text
1. 写入 tmp/<随机名>            （边写边计算块 CRC 与客户端声明的校验和）
2. fsync 数据文件
3. 将块提交到 cas/<xx>/<sha256>  （内容寻址；若已存在则跳过，即去重）
4. 写 tmp/<随机名>.meta         （新元数据）
5. fsync 元数据文件
6. rename 到 objects/<xx>/<sha256>/meta.json   （原子替换）
7. fsync 父目录
```

**关键保证**：第 6 步的 `rename` 是原子的。崩溃发生在第 6 步之前 → 对象不存在（旧版本仍在）；发生在第 6 步之后 → 对象为完整新版本。**任何时刻都不会出现"对象存在但内容残缺"的状态。**

`--fsync-policy` 可配置为 `always`（默认，每步 fsync）或 `meta`（仅元数据 fsync，吞吐更高、掉电窗口更大）。这是可靠性与吞吐的显式权衡，默认取可靠性。

## 读路径

- 大对象 GET 使用 `sendfile` 零拷贝：定位偏移、声明 `Content-Length`、直接搬运数据，避免用户态缓冲区拷贝。
- Range 请求在块边界内直接定位，不读取无关块。

### 真实张力：校验读 vs 零拷贝读

**验证读（逐块校验和）与零拷贝读（sendfile）在原理上互相冲突**：校验必须将数据读入用户态，零拷贝则刻意避开用户态。

面向边端真实负载取舍：

- **写入时**：全量校验（CRC32C + 客户端声明的校验和），确保落盘数据正确。
- **读取时**：默认**不**逐块校验，走零拷贝路径，保障模型加载吞吐。
- **后台**：GC goroutine 顺带执行低优先级 scrub，检出静默损坏并记录指标。
- **可选**：按 bucket 或全局配置启用"读取时校验"，用于对可靠性要求高于吞吐的场景。

两模式的性能差距必须由 `BenchmarkGetRangeSequential`（零拷贝）与开启校验后的对照数据量化，**不得只凭推断**。

## 崩溃恢复

启动流程设计目标是**与已存对象数量弱相关**，不做全量数据扫描：

1. 读取并校验 `blink-meta.json`；若格式版本高于本二进制支持的版本，**拒绝启动**并给出明确错误（防止旧版本损坏新数据）。
2. 清扫 `tmp/` 中的残留文件 —— 这些必然是未提交的写入。
3. 清扫未完成的分片上传（超过保留期的 `multipart/` 状态）。
4. 桶目录自愈：`bucket.json` 缺失或损坏时按最小元数据重建，而非让整个桶不可用。
5. 启动后台 GC 与 scrub。

**明确不做**：启动时不遍历 `cas/` 做完整性全盘校验（代价与对象数量成正比，违背"与规模弱相关"目标）。损坏在读取或 scrub 时才发现并上报。

**限制**：macOS 上无法可靠模拟掉电，因此"fsync 后 rename 前"这一关键窗口由故障注入测试覆盖；真实掉电场景**未测试**，记录在 `docs/design/known-limitations.md`。

## 并发与锁

| 场景 | 策略 |
| --- | --- |
| 同一 key 的并发写 | 对象级锁，最终以最后一次原子 `rename` 为准，读者不撕裂 |
| 不同 key 的并发写 | 完全并行，互不阻塞 |
| 读与写并发 | 无锁；依赖 `rename` 原子性与 CAS 不可变性 |
| 分片上传 | 各分片独立写入，`CompleteMultipartUpload` 时统一提交 |

## 垃圾回收

- **孤儿块**：CAS 中未被任何 `meta.json` 引用的块。带**宽限期**（默认 1 小时）后回收，避免误删在途写入的块。
- **临时文件**：启动时清扫 + 定期清扫超过保留期的残留。
- **分片上传残留**：超过保留期的未完成上传自动中止并清理。
- **可回收空间**：通过 `blink_disk_reclaimable_bytes` 指标暴露，让运维理解"删除对象后空间未立即释放"是由于去重共享或宽限期。

**去重的语义边界**：同一内容被多个对象引用时，删除其中一个对象不会释放空间（其它对象仍引用该块）。这一点必须在文档中明确，避免用户误认为删除立即释放磁盘。

## 磁盘容量管理

| 参数 | 默认值 |
| --- | --- |
| 高水位 | 0.90 |
| 低水位 | 0.85 |

- 超过高水位：拒绝新的写入（PUT / 分片上传），返回 `507 InsufficientStorage`。
- **降至低水位以下才恢复接受写入**（滞回区间，避免在阈值附近抖动）。
- **满盘时读与删除必须仍然可用** —— 否则用户无法通过删除释放空间自救。
- 水位与可回收空间通过 `/readyz` 字段与 Prometheus 指标暴露。

**已确认（2026-10-26）**：满盘返回 `507 InsufficientStorage`，`/readyz` 保持 `200` 并暴露水位字段。依据是主流实现的行为：MinIO 与 Dell ECS/ObjectScale 均以 507 表示容量耗尽，AWS 的 `503 SlowDown` 仅表示请求限流；健康检查不把容量耗尽等同于进程未就绪。详见 `docs/design/known-limitations.md`。

## 创新点

以下创新项面向边端 AI 推理的真实负载。**所有未由基准数据支撑的收益均标注为待验证假设，不得作为性能承诺。**

| 创新 | 本版本 | 实现成本 | 验证方式 |
| --- | --- | --- | --- |
| **A. 内容寻址块 + 每块 CRC32C，跨桶/跨 key 天然去重** | ✅ 纳入 | 低（布局自带） | `BenchmarkDedupSecondCopy/1GiB` 断言写入字节数不增长 |
| **B. 分片上传完成时仅串接块表，不重写数据** | ✅ 纳入 | 中 | `BenchmarkCompleteMultipart20GB` 断言耗时与写入量不随对象增长 |
| **C. `sendfile` 零拷贝读路径 + 顺序预读** | ✅ 纳入 | 低 | `BenchmarkGetRangeSequential` 前后对照 |
| **D. 小对象打包为只读 segment（needle 思路）** | ⏸ 延后至切片 9 | 高 | `BenchmarkPutSmallObject10k`、`BenchmarkList100kObjects` 前后对照 |
| **E. 批量写与非标准 API** | ❌ 不做 | — | 保持"任意 S3 客户端可用"，不引入非标准接口 |
| **F. 预热 / pin 接口** | ❌ 不做 | — | 零拷贝与内核页缓存已使热点模型自然驻留 |
| **F'. TTL bucket（中间结果自动过期）** | ⏸ 配置驱动的后台任务，切片 9 之后 | 低 | 属策略而非机制，不占用首个切片注意力 |

**为什么创新 B 对边缘场景重要**：20 GiB 模型的分片上传若在完成时重写全部数据，在 eMMC/SD 卡上会产生数十 GiB 的额外写入（写放大），显著缩短介质寿命。仅串接块表可将完成操作的开销与对象大小解耦。

**开发纪律**：创新 D 是唯一"必须先有基线基准数据、再决定是否合入"的项。任何没有前后 benchmark 对照的优化一律回滚。

## 分布式预留接缝

**首个版本为单节点设计，但代码结构不得假设"只有本机"。** 以下接缝在本版本中不实现任何分布式行为，仅预留扩展点，且在单机模式下必须零额外开销：

| 接缝 | 位置 | 当前行为 | 未来用途 |
| --- | --- | --- | --- |
| `node_id` | `blink-meta.json` | 首次启动生成并持久化 | 集群节点身份 |
| `Placement` 接口 | `internal/cluster` | 恒返回本机 | 分片与副本定位 |
| `ChangeFeed` 事件钩子 | 每次成功写/删后发射 | 无订阅者时为空操作 | 复制与同步引擎订阅 |
| `BlockFetcher` 接口 | 块读取路径 | 只读本地 CAS | 远程拉取块 |
| `Store` 接口边界 | S3 API 层仅依赖该接口 | 单机文件系统实现 | 集群实现替换 |
| `obj_version` + `node_id` | `meta.json` | 单调递增、记录来源节点 | 冲突检测与解决 |
| `Cluster{}` 配置段 | 配置 | `Mode: single` | 后续模式扩展；未知模式拒绝启动 |

**明确不做**：节点发现、成员管理、共识协议、数据复制、跨节点请求转发。

## 验收要求

设计必须给出数据损坏、进程中断、磁盘满和重复写入时的行为；实现必须有恢复测试、并发读写测试和可观测的失败原因。

| 场景 | 要求行为 |
| --- | --- |
| 数据块损坏 | 读取或 scrub 时检出，返回明确错误并记录块哈希，不静默返回错误数据 |
| 进程中断 | 恢复后对象只可能"不存在"或"内容完整"，绝不残缺 |
| 磁盘满 | 写入返回 `507 InsufficientStorage`，临时文件被清理，读与删除仍可用 |
| 重复写入 | 相同内容不重复占用磁盘（去重），且元数据正确指向已存块 |
